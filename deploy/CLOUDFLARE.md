# Cloudflare in front of the VPS

The VPS already has another service bound to port 443, so nginx cannot own that
port and certbot cannot complete a TLS handshake on it. Cloudflare terminates
TLS at the edge instead, and reaches the origin over plain HTTP on port 80.

This file supersedes **step 7 (TLS)** of `README.md`. Steps 1 to 6 still apply,
with the additions in "Gaps in the base setup" below.

---

## What Flexible mode actually does

| Leg | Encrypted |
|---|---|
| Visitor → Cloudflare | yes |
| Cloudflare → VPS | **no, plaintext over the public internet** |

Visitors see a padlock. The hop from Cloudflare to the VPS is readable by
anything on the path between them. For a public portfolio that serves no
credentials and no personal data beyond what is already published on the page,
the exposure is small, but it is not zero and it is worth removing later. See
"Getting off Flexible" at the end.

The mitigation that matters now is closing port 80 to everyone except
Cloudflare, so the plaintext leg is at least not reachable by the open
internet. That is step 4 below.

---

## Hard rules under Flexible

Three of these will take the site down if broken.

1. **The DNS records must be Proxied (orange cloud).** With a grey cloud, the
   name resolves straight to the VPS and `https://rafidazhar.dev` hits port 443
   directly, which is the other service, not this site. Proxied is what makes
   Flexible work at all.

2. **Never add an HTTP to HTTPS redirect on the origin.** Cloudflare arrives
   over HTTP. If nginx answers with a 301 to `https://`, Cloudflare follows it
   by requesting the origin over HTTP again, gets the same 301, and loops until
   the browser gives up with `ERR_TOO_MANY_REDIRECTS`.

3. **Do not run certbot.** `README.md` step 7 runs
   `certbot --nginx --redirect`, and `--redirect` inserts exactly the redirect
   rule that rule 2 forbids. Skip that step entirely. `deploy/nginx.conf` is
   HTTP only by design, which is already the correct shape here.

Redirecting HTTP to HTTPS is still fine, but it has to happen at the **edge**,
where no loop is possible: turn on Cloudflare's "Always Use HTTPS". That is
step 2 below.

## 1. Cloudflare dashboard

**DNS → Records**

| Type | Name | Content | Proxy |
|---|---|---|---|
| A | `@` | your VPS IPv4 | Proxied |
| CNAME | `www` | `rafidazhar.dev` | Proxied |

Add an `AAAA` for `@` only if the VPS has a routable IPv6 and nginx is
listening on it. A proxied `AAAA` pointing at an address nginx does not answer
on produces intermittent 522s that are painful to trace.

**SSL/TLS → Overview**

Set the mode to **Flexible**.

**SSL/TLS → Edge Certificates**

- Always Use HTTPS: **On**
- Minimum TLS Version: 1.2

## 2. Confirm what is already listening

Before touching the firewall, see what the box is actually running, so nothing
existing gets cut off:

```bash
sudo ss -tlnp
```

Note every port you need to keep reachable. Port 443 will be in that list.

## 3. nginx hostname

`deploy/nginx.conf` ships with a placeholder rather than a baked-in origin:

```bash
sudo cp deploy/nginx.conf /etc/nginx/sites-available/rafidazhar && sudo sed -i "s/REPLACE_WITH_HOSTNAME/rafidazhar.dev www.rafidazhar.dev/" /etc/nginx/sites-available/rafidazhar && sudo ln -sf /etc/nginx/sites-available/rafidazhar /etc/nginx/sites-enabled/ && sudo nginx -t && sudo systemctl reload nginx
```

Do not edit this file to add TLS. Under Flexible there is no certificate on the
origin and nothing to configure.

## 4. Restrict port 80 to Cloudflare

Without this, anyone who learns the VPS IP can bypass Cloudflare entirely and
read the plaintext origin directly.

The ranges change occasionally, so generate the rules from Cloudflare's own
published lists rather than pasting a snapshot:

```bash
sudo ufw allow OpenSSH && for ip in $(curl -fsS https://www.cloudflare.com/ips-v4) $(curl -fsS https://www.cloudflare.com/ips-v6); do sudo ufw allow from "$ip" to any port 80 proto tcp comment 'cloudflare'; done
```

**Before enabling ufw**, add rules for everything you noted in step 2 or those
services will go dark the moment the firewall comes up:

```bash
sudo ufw allow 443/tcp
```

Then:

```bash
sudo ufw enable && sudo ufw status numbered
```

## 5. Real visitor IPs in the logs

Every request now originates from a Cloudflare address, so without this the
access log records Cloudflare instead of visitors:

```bash
{ for ip in $(curl -fsS https://www.cloudflare.com/ips-v4) $(curl -fsS https://www.cloudflare.com/ips-v6); do echo "set_real_ip_from $ip;"; done; echo "real_ip_header CF-Connecting-IP;"; } | sudo tee /etc/nginx/conf.d/cloudflare-realip.conf && sudo nginx -t && sudo systemctl reload nginx
```

## Gaps in the base setup

`README.md` step 2 creates the deploy user with `adduser --system`, which on
Debian and Ubuntu assigns `/usr/sbin/nologin` as the shell. `deploy.sh` needs
to `ssh` and `rsync` as that user, and both need a real shell. It also runs
`sudo systemctl restart rafidazhar`, which needs a sudoers rule since the
system account has no password to type.

Give the account a shell and your key:

```bash
sudo usermod --shell /bin/bash deploy && sudo mkdir -p /srv/rafidazhar/.ssh && sudo chmod 700 /srv/rafidazhar/.ssh
```

Append your public key (run this from your **local** machine):

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub deploy@YOUR_VPS_HOST
```

If the account rejects that because it has no password, paste the key as root
on the VPS instead:

```bash
sudo tee -a /srv/rafidazhar/.ssh/authorized_keys < /dev/stdin && sudo chown -R deploy:deploy /srv/rafidazhar/.ssh && sudo chmod 600 /srv/rafidazhar/.ssh/authorized_keys
```

Then the restart permission. Check the binary path first, because the sudoers
rule matches the literal path sudo resolves:

```bash
command -v systemctl
```

Use whatever that prints:

```bash
echo 'deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart rafidazhar' | sudo tee /etc/sudoers.d/rafidazhar-deploy && sudo chmod 440 /etc/sudoers.d/rafidazhar-deploy && sudo visudo -c
```

## Verifying

On the VPS, confirm the origin answers on plain HTTP for the right vhost:

```bash
curl -fsS -o /dev/null -w '%{http_code}\n' -H 'Host: rafidazhar.dev' http://127.0.0.1/
```

From your machine, confirm the edge is serving and that there is no loop. A
healthy result is a single `HTTP/2 200` with a `cf-ray` header:

```bash
curl -sIL https://rafidazhar.dev | grep -Ei '^(HTTP|cf-ray|server)'
```

Confirm the HTTP entry point redirects once, at the edge:

```bash
curl -sI http://rafidazhar.dev | grep -Ei '^(HTTP|location)'
```

Confirm the origin is no longer reachable directly:

```bash
curl -sS --max-time 5 http://YOUR_VPS_IP/ ; echo "exit: $?"
```

A timeout here is the correct outcome.

### If you get ERR_TOO_MANY_REDIRECTS

Rule 2 was broken. Something on the origin is redirecting to HTTPS. Check:

```bash
sudo grep -rn "return 301\|rewrite.*https\|listen 443" /etc/nginx/sites-enabled/
```

Certbot having been run at some point is the usual cause. Remove the redirect
block and the 443 server block it added, then reload.

### If you get 521 or 522

522 is a connection timeout from Cloudflare to the origin: the firewall is
blocking Cloudflare, or nginx is not listening. 521 means the origin actively
refused. Check in order:

```bash
sudo systemctl status nginx rafidazhar && sudo ufw status && sudo ss -tlnp | grep ':80'
```

## Getting off Flexible

All three of these encrypt the Cloudflare to origin leg. Listed cheapest first.

**Move the other service off 443.** xmrig-proxy's bind port is configurable and
pools generally accept any port. Freeing 443 means `README.md` step 7 works as
written: real certificate, and Cloudflare SSL/TLS mode goes to **Full
(strict)**. This is the least moving parts of the three.

**Cloudflare Tunnel.** Install `cloudflared` on the VPS and run a tunnel to
`http://127.0.0.1:3000`. The tunnel dials out, so the origin needs **no inbound
ports open at all**. The 443 conflict stops mattering, the firewall rules in
step 4 become unnecessary, and the hop is encrypted. Best security outcome, at
the cost of one more daemon to keep running.

**Full (strict) on an alternate origin port.** Terminate TLS in nginx on 8443
with a certificate, then use a Cloudflare Origin Rule to override the origin
port. Works, but it is the fiddliest of the three and the Origin Rule is easy
to forget when debugging later.

Whichever you pick, switch the SSL/TLS mode to Full (strict) only **after** the
origin genuinely serves a valid certificate, or every request returns 526.
